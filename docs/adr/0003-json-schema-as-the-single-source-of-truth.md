# 0003. JSON Schema as the single source of truth

- **Status:** Accepted
- **Date:** 2026-07-27

## Context

`plan.md` §1 says "the spec prose and schemas must agree; schemas win for machines,"
and §3 Stage 1 requires TypeScript types generated from schemas with a CI drift
check. That establishes the *direction* of truth but leaves three things undecided,
each of which is frozen forever the moment a tag ships:

1. the schema dialect and how `$id`/`$ref` are written;
2. which validator the mock-agent and the harness use at runtime;
3. how "additive-only" is expressed mechanically, not just as prose.

Three consumers read these shapes: the harness (validates a live agent's responses),
the mock-agent (produces them), and `nightshift-client` (types only, no runtime
validation). A TypeScript-first source of truth would serve the client best; a
schema-first one serves the other two, and is the only option that can validate a
*non-TypeScript* agent — which the spec must permit.

## Decision

- **Dialect:** JSON Schema 2020-12, one file per wire shape under `schemas/`.
- **`$id` prefix, frozen:**
  `https://seanerama.github.io/agent-app-contract/schemas/v1/<shape>.json`
  Cross-schema `$ref`s use the same absolute prefix. The URL need not resolve —
  it is an identifier — but GitHub Pages *can* later be enabled on this repo to make
  it resolve, without reissuing a single `$id`. The `/v1/` segment carries the
  contract version; a hypothetical v2 lives at `/v2/` and is a different namespace.
- **Runtime validator:** `ajv` (2020-12 mode), used by both `mock-agent` and
  `conformance`, each compiling the schemas independently from `schemas/`.
- **Types:** generated by `json-schema-to-typescript` into `packages/types`, output
  **committed**, with a CI job that regenerates and fails on any diff. Types are a
  build artifact of the schemas, never hand-edited.
- **Tolerant readers:** `additionalProperties` is left unset (open) on every object
  schema. Validators MUST NOT reject unknown fields. This is the mechanical
  expression of additive-only: a v1.1 agent may send fields a v1.0 client has never
  heard of, and nothing breaks.
- **Required-field rule:** additive changes may add optional fields and new enum
  members to *outbound* shapes. Adding a `required` field, narrowing a type, or
  removing an enum member is a breaking change and therefore a new contract, never an
  edit (per the contracts-first guide).

## Alternatives considered

The **contracts-first guide** mandates only that a frozen contract is never broken;
it does not prescribe a schema technology. It is followed exactly.

- **TypeScript types as the source, schemas generated** (e.g. via `zod` +
  `zod-to-json-schema`, or `typebox`). Rejected: it makes the normative artifact a
  TypeScript file, which quietly declares that agents should be written in
  TypeScript. The contract must be equally implementable in Python or Go, and a
  vendor of the spec must be able to read `schemas/` without a Node toolchain.
- **OpenAPI instead of bare JSON Schema.** Genuinely attractive — it would describe
  routes, status codes, and auth in one machine-readable document, and could generate
  a client. Rejected for v1 on two grounds: the SSE event stream and the MCP endpoint
  are both poorly expressed in OpenAPI, so the document would be authoritative for
  part of the surface and misleading for the rest; and it would put a code generator
  between the spec and the harness, weakening ADR-0005's independence argument.
  Revisit if the surface ever becomes purely request/response.
- **`urn:` `$id`s** (`urn:nightshift:app-ingress:v1:manifest`). Honest about being an
  identifier rather than a location, and host-independent. Rejected: several JSON
  Schema toolchains handle non-http `$id` and `$ref` resolution poorly, and the
  github.io form is equally stable while retaining the *option* of resolving.
- **`raw.githubusercontent.com` `$id`s.** Resolve today with zero setup. Rejected:
  they bake a git ref into the identity of the schema and point at GitHub's serving
  infrastructure rather than a namespace we control.
- **Closed schemas (`additionalProperties: false`).** Would catch typos in agent
  implementations. Rejected outright: it makes every additive spec change a breaking
  change for every older reader, which contradicts the repo's core promise.

## Consequences

- The github.io `$id` prefix is a promise. If this repo is ever renamed or moved to
  an org, the `$id`s must **not** change — they become historical identifiers that no
  longer match the repo's location. That is acceptable and normal for schema `$id`s,
  but it must not be "fixed" by a well-meaning later PR.
- Open `additionalProperties` means the harness cannot detect an agent sending junk
  fields. That is the deliberate trade: false-green on stray fields is cheaper than
  false-red on forward compatibility.
- Committed generated types mean every schema PR carries a regenerated-types diff.
  Reviewers must read the schema change and treat the type diff as derived output.
- `ajv` becomes a runtime dependency of both published programs. Compiling schemas
  twice (once per package) is intentional duplication, not waste — see ADR-0005.
- Any future v2 gets a new `$id` namespace and a new directory. `schemas/v1/` is
  never edited after `v1.0.0`, only added to.
